01 / Architecture

Eight layers.
Clear responsibilities.

01–04 / Adaptive intelligence05–08 / Deterministic execution
01 / Signal Intelligence

Perceive. Proprietary AI and machine-learning models generate risk, price and opportunity signals, with regime detection and continuous re-estimation. In Lifecycle 01, inputs include ETF price, net asset value (NAV), basket composition, borrow and venue depth.

02 / Model Layer

Reason. A post-trained large language model is tuned on each lifecycle's documents, rules, message formats and exception history, and evaluated per release. Tool use is bounded by the layers below: the model can propose an action, but cannot execute it on its own.

03 / Domain-Specific Agents

Act. Each agent has a narrow, verifiable job and only the tools it needs. One-click workflow creation and exception management coordinate those jobs; the Execution Council arbitrates between them.

The master–copy model replicates a proven master agent, then specializes copies by asset, venue or customer. The architecture is designed for 5,000–50,000 agents per lifecycle, sharing one Council and one ledger.

04 / Execution Council

Govern. The Council applies policy and mandate limits, arbitrates conflicting proposals, and returns approve or reject before execution. Human approval is required when the operating mode calls for it. Rejected proposals are recorded too.

05 / Routing Layer

Optimize. Approved actions are routed using venue conditions, execution costs, historical performance and latency budgets. In Lifecycle 01, routing spans brokers, over-the-counter desks, dark pools, exchanges and clearing rails.

06 / Execution Layer

Orchestrate. A deterministic state machine tracks validated → submitted → partial → filled → reconciled. Explicit preconditions, idempotency keys, retries, backoff and reconciliation against counterparty records keep action handling separate from model output.

07 / MCP Server

Connect. A custom Model Context Protocol (MCP) server exposes authenticated tools and a real-time data pipe. Customer-scoped deployments keep tools and context separate, with adapters for brokers, transfer agents, custodians, execution desks, exchanges and clearing.

08 / Authentication Layer

Permit. Role-based access and scoped, revocable API permissions govern each agent, tool and counterparty. In Lifecycle 01, custody stays at the broker and the system has no withdrawal permissions.

02 / The control boundary

Agents decide.
Code executes.

A proposal is not an action. Policy gates come first. Explicit state transitions follow. A shared, append-only, hash-chained ledger records both.

01 / Before action

Validate.

Check schemas, policy, limits and required approvals before an action reaches execution.

02 / During action

Submit.

Track state, confirmations and retries. Idempotency keys protect against duplicate submissions.

03 / After action

Reconcile.

Match internal records to counterparty records. Raise discrepancies; preserve the trail.

Operating modes & emergency halt

Fully automatic. The Council approves actions within the configured policy and mandate.

Auto-with-approval. Agents propose; an operator or delegate confirms before execution.

Manual. Agents recommend; the operator decides and initiates action.

A database-backed emergency halt is available in every mode. In Lifecycle 01, checks also include market hours, position and notional caps, and instrument-level constraints.

Deployment & lifecycle scope

Each deployment has its own toolset, adapters and customer context. The real-time data pipe carries provenance and latency budgets; in Lifecycle 01 it supplies prices, NAVs, baskets, confirmations and reference data.

Orchestration, governance, authenticated tools and execution state form the reusable substrate. A new lifecycle still needs its own domain corpus, agents, adapters and policy evaluation. Explore the roadmap

Third-party agents / roadmap

A future marketplace would let builders publish agents and lifecycles with workflow constraints, Council approvals and role-based controls. Operators would inspect execution records and evaluate lifecycle behavior before deployment. This is platform direction, not a claim of current marketplace availability.
